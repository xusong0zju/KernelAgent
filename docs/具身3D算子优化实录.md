# 具身/3D 算子优化实录（Voxelization + BEV Lift-Splat）

> 用 KernelAgent 闭环（本机 deepseek-v4-pro + 云端 RTX 2080 Ti）优化两个具身/3D 感知算子，
> 选型依据 `docs/世界模型热点算子调研报告.md` §4.3/§4.4。
> 写于 2026-07-24。

---

## 一、选型

从调研报告 §4 具身/3D 蓝海里，按 KernelAgent 闭环适配性（单 kernel + 有 eager baseline + 单卡可验证 + memory-bound 融合空间）筛出两个：

- **点云 Voxelization**（§4.3）：N 点 → [256,256,8] voxel 网格均值池化。LiDAR 预处理。优化空间 = fused hash+pool，减少原子竞争。
- **BEV Lift-Splat**（§4.4）：6 相机 feat × depth → scatter-add 到 BEV。优化空间 = fused 不物化外积（B·C·H·W·D 巨张量）。

## 二、结果

| 算子 | eager | Triton naive | Triton 优化(LLM) | Triton 向量化 | CUDA naive | CUDA 归约 | 最佳 |
|---|---|---|---|---|---|---|---|
| Voxelization | 0.55 | 0.557 | 0.456 | **0.370** / 0.118(sorted) | 0.274 | 0.246 | 见下方深度对照 |
| BEV lift-splat | 0.308 | — | 0.137（已fused） | — | — | — | Triton 0.137 |

> Voxelization 的最佳不是单一数字——取决于**输入是否有序** + **用 Triton 还是 CUDA**。完整对照见下节"深度对照"。一句话：**输入有序时 Triton 向量化(0.118)≈CUDA(0.104)；输入随机时 CUDA(0.274)仍比 Triton 向量化(0.370)快 1.35x，差距来自编译器非表达力**。

### Voxelization 的 CUDA vs Triton 深度对照（核心，含错误归因的修正）

Triton 优化到 0.456ms 后触顶。我最初把"CUDA 比 Triton 快"归因于"Triton 表达力不足、写不出 block 归约"。**事后严格对照实验推翻了这个归因**——真因是编译器质量，不是表达力。完整推理与实测如下。

#### 实验 1：CUDA v1 的 block 归约到底有没有生效

CUDA v1 做"block 内按 thread 顺序找相邻同 voxel 段、段首单次 atomic"。**但点没全局排序**——200K 点 / 524K voxel 平均每 voxel 0.38 点，相邻 thread 同 voxel 概率低，怀疑归约几乎不生效。

**对照**：同一 CUDA v1 kernel，输入分 random vs "按 voxel 排序后"（voxelization 对点序不敏感，排序是合法变换）：
- random: 0.249ms
- sorted: **0.101ms**（快 2.5x）

**结论**：sorted 下归约充分生效（同 voxel 相邻、段长=同 voxel 点数），0.101 是"归约生效"性能；random 下归约部分生效（0.249）。**归约确实有用，但 random 下因点稀疏收益有限**。

#### 实验 2（决定性）：隔离"归约" vs "编译器质量"

写 **CUDA naive**（朴素 5-atomic，**去掉 v1 的 block 归约和 shared mem**，与 Triton naive 同结构），三者在 random/sorted 下对照：

| | random | sorted | sorted/random |
|---|---|---|---|
| triton_naive（5原子，无归约） | 0.557 | 0.264 | 0.47 |
| **cuda_naive（5原子，无归约，同结构）** | **0.274** | **0.104** | 0.38 |
| cuda_v1（有 block 段归约） | 0.246 | 0.100 | 0.41 |

两个关键发现：
1. **cuda_naive vs cuda_v1**：random 0.274→0.246（归约仅省 10%），sorted 0.104→0.100（几乎没差）。**block 归约在此 shape 只值 ~10%**——不是 CUDA 快的主因。
2. **triton_naive vs cuda_naive（同结构！）**：random 0.557 vs 0.274 → CUDA 快 **2.03x**；sorted 0.264 vs 0.104 → CUDA 快 **2.54x**。**这 2-2.5x 纯粹来自编译器**（nvcc vs Triton LLVM 后端：float4 向量化 load、atomic 指令 lowering、cache line 合并），不是算法/表达力。

#### 实验 3：sorted 让两者都大幅加速——是局部性，不是归约

- triton_naive（无归约）sorted 0.264 = cuda_naive（无归约）random 0.274 ≈ 相等
- 即"点排序获得 atomic 局部性"≈"CUDA 编译器优势"，两个独立因素量级相当
- sorted 下两者都接近理论（cuda 0.104，离带宽下限 0.022 还有 4.7x，剩余是 atomic 吞吐本身）

#### 修正后的正确归因

我之前的"Triton 表达力限制"归因**双重错误**：
1. ~~"CUDA 快是因为 block 归约降了原子数"~~ → 归约只贡献 10%，主因是编译器
2. ~~"Triton 写不出归约所以慢"~~ → 即使写出来（cuda_naive 无归约），Triton 仍慢 2x

**正确结论**：CUDA 优于 Triton 的 2-2.5x **主要来自编译器质量**（nvcc 对 atomic + float4 load 的优化强于 Triton LLVM 后端），**不是表达力/归约**。block 段归约在此 shape（点稀疏）只值 ~10%。排序局部性和编译器优势是两个独立、量级相当的加速源。

### Triton 能否翻倍（向量化移植实验）

既然 CUDA 优势来自 float4 load + 2D atomic，把它移植回 Triton：用 `tl.load` 2D block ptr 一次读 [BLOCK,4] + `tl.atomic_add` 2D 一次加 4 维（替代 4 次标量 atomic）。

| 方案 | random | sorted | vs triton_naive |
|---|---|---|---|
| triton_naive（基线） | 0.557 | 0.264 | — |
| **triton_vec（2D load+atomic）** | **0.370** | **0.118** | random 1.5x / sorted **4.7x** |
| triton_presort（含 argsort） | 0.567 | — | argsort 0.45ms 吃光收益，净亏 |
| cuda_naive（对照） | 0.274 | 0.104 | — |

发现：
- **sorted 下 triton_vec 0.118 ≈ cuda_naive 0.104**——向量化后编译器差距从 2.54x 缩到 1.14x，**几乎抹平**。即输入有序时 Triton 能逼近 CUDA。
- **random 下 triton_vec 0.370**——快 1.5x（没翻倍到 0.27）。剩余差距是 nvcc 在高冲突下更强的 cache-line atomic 合并，Triton 后端做不到。
- **预排序不划算**：wrapper 内 argsort 0.45ms，把向量化省的 0.18ms 全吃了还倒贴。除非点云**天然空间有序**（真实 LiDAR 扫描线常有序），否则预排序不是免费午餐。

**回答"Triton 能否再翻倍"**：
- 输入有序时能（0.557→0.118，4.7x，远超翻倍）——但要求输入免费有序
- random 输入下不能——向量化到 0.370 是当前极限，再压受 nvcc 的 cache-line atomic 合并优势限制

### 实践指引（给后续算子选型）

1. **atomic-bound 的 scatter 类算子**：优先看输入是否天然有序。有序→Triton 向量化即可逼近 CUDA；无序→CUDA 编译器优势 2x，Triton 难追。
2. **不要把"CUDA 快"轻易归因于"Triton 表达力"**——先用 naive 同结构对照隔离编译器差距，再判归约/算法贡献。我这次就是没做同结构对照就下了错误结论。
3. **block 归约对"点稀疏"shape 收益小**（~10%）——别为追求归约强行上复杂结构，先量化同 voxel 冲突密度。
4. **向量化 load/atomic**（2D block ptr）是 Triton 端便宜且确定的提升（1.5x），优先尝试，比 block 归约 ROI 高。

## 三、关键发现

### 发现 1（最重要）：thinking budget 是推理模型的解药

**症状**：deepseek-v4-pro 对复杂算子 prompt 大概率"全程思考、不产出最终代码"（`_extract_text` 拿到 `len=0` 的纯 thinking 响应）。RMSNorm 简单能成功，voxelization 复杂就卡。

**根因**：推理模型的 thinking 会吃光 `max_tokens` 预算，最终 text 答案没空间产出。

**解药**：金山云网关支持 Anthropic 的 `thinking` 参数，**限制 `budget_tokens`**（让思考别太长，给答案留空间）。实测 `budget=4096` 让 voxelization prompt 稳定产出闭合可运行代码。

**关键认知**：这与"effort 调 max"**相反**——max 让思考更长、答案更可能被挤掉；调小 budget 才是正解。

**已固化**：`AnthropicProvider.get_response` 支持 `ANTHROPIC_THINKING_BUDGET` env（不设时向后兼容）。见 `utils/providers/anthropic_provider.py`。

### 发现 2：Triton 表达力边界（BEV 难突破的根因）

BEV 的"深度维 D 循环 + 每个 d 一个标量线性地址 scatter"，Triton **不支持向量索引 `lin[i]`**（`unsupported tensor index: constexpr[0]`）。LLM 反复踩：`lin[i]`、`wgt[i]`、`d_mask[i]` 全不行——必须逐 d 全标量算。

这导致 BEV 的 baseline（逐 (b,h,w) 程序 + 逐 d 标量 atomic）已是该结构在 Triton 下的接近天花板实现。要更快需更聪明的 tiling（多 (h,w) 共享坐标），但表达受限。

**结论**：KernelAgent 优化受**底座模型能力 + Triton 表达力**双重约束。结构友好的（voxelization 点→voxel 单映射）能优化；结构需要 Triton 难表达操作的（BEV 的 D 维向量 scatter）难突破。

### 发现 3：闭环对失败正确丢弃

多轮里 LLM 产出 `continue`（JIT 不支持）、`_semantic`（内部 API）、`tl.static_shared`（不存在）、缺逗号等错误代码，**全部被云端 verify 客观拒绝，best 不被污染**。这是 KernelAgent 相对直接用 LLM 的核心价值实锤。

## 四、踩坑（Triton JIT 语法，LLM 反复踩，已加进 prompt 约束）

- `t[:, i]` 2D 列切片不支持 → 用 1D load
- `lin[i]` / `wgt[i]` 向量用 constexpr 索引不支持 → 标量逐个算
- `.clamp` 不存在 → `tl.maximum/tl.minimum`
- `continue`/`break` 在 @triton.jit 内不支持 → 用 mask
- `tl.static_shared`/`tl.shared`/`_semantic` 不存在 → 用寄存器 + `tl.atomic_add`
- `tl.arange`/`tl.static_range` 的参数必须 constexpr

这些已写进 `examples/optimize_kernel_remote.py` 的 OPT_PROMPT 约束段，降低 LLM 失败率。

## 六、复现

```bash
# 1. 部署 daemon（见 docs/远程GPU部署.md，--python-bin ka_gpu）
# 2. 跑优化（必须设 thinking budget）
env -u ALL_PROXY -u all_proxy \
  OPENAI_MODEL=deepseek-v4-pro ANTHROPIC_THINKING_BUDGET=4096 \
  ~/miniconda3/envs/kernel_agent/bin/python examples/optimize_kernel_remote.py \
    --kernel-dir examples/optimize_voxelization \
    --url http://127.0.0.1:8765 --token <token> --rounds 3
```

**注意**：复杂算子必须设 `ANTHROPIC_THINKING_BUDGET`（4096 量级），否则推理模型大概率不产出代码。
